# Floggfy 1.4 function review

Start with the capture queue, the release-audit memory reservation, and the Saved catalog's handling of read errors. Each has a concrete failure mode or repeatable cost. Splitting files is a separate maintenance task. In particular, `audio_history.cpp` is 4,357 lines, but its largest individual function spans 302. Moving code into more files on its own will not shorten a lock hold or fix a false “unsaved” result.

| Order | Change | Evidence and acceptance check |
|---|---|---|
| 1 | Make capture release auditing charge its reservation once and shorten the shared budget lock. | `CheckBeforeRelease` holds the lock during flattening and codec validation while the capture worker needs it for incoming events. Replay a large capture near the memory limit concurrently with new input. Check peak bytes, recovery after rejection, worker wait and dropped events. |
| 2 | Copy only the used payload in `audio_history.cpp::Pop` and the stream-dump writer. | The capture slot has a 65,307-byte array and the dump record has a 65,536-byte array. Each is copied in full under its queue lock, even for small control events. Compare mixed small/full events, preserve event order and ensure the consumer owns the bytes before the slot is reused. |
| 3 | Return an explicit failure from Saved catalog reads. | `Database::Rows` treats a prepare/read error as an empty or partial result. `AnswerQuery` can publish a missing date. Inject a read failure after one row and verify the previously known date survives until a successful retry. |
| 4 | Skip full-list date work after a Saved sort settles. | `apply` and `requestDates` repeatedly traverse playlist-sized collections. In the existing 2,651-entry case, count visits and allocations on idle polls, then change one date and confirm sort order and blanks update. |
| 5 | Check for unchanged work before building tags or paths. | `QueueFilenameCheck` prepares metadata before its duplicate-key check. `PublishSongDestination` can construct 20 paths per unchanged observation. Exercise repeated playback notifications and a real save-folder change. |
| 6 | Retire wrappers with only test callers. | `InspectOwnedMp3` wraps the richer inspection result. Update tests to assert the actual result. `WriteRecord` forwards one element to `WriteBatch`; call the latter from the tests. Check production and conditional Windows callers before deleting either declaration. |

## Source and scope

The inventory contains 3,544 entries across 233 files, including 1,927 runtime entries and 1,617 test and tooling entries. Counts include compiler-special members and macro-generated forwarders. The inventory uses the v1.4 release tree (`1e3d67a90442b46126fcf35cd6a79eca66b704e6`) and paths after the test-runner move. Each CSV row identifies a definition by file, one-based line and column, including overloads, inline methods, nested callbacks and lambdas. Filter by disposition to find proposed changes. The detailed reviews also cover surrounding callers and related functions.

- [Runtime function inventory](runtime.csv) covers first-party native code, headers, the five renderer scripts, the 17 assembly export forwarders and the 12 socket wrappers generated by the project macro.
- [Test and tooling inventory](tests-tools.csv) covers test callbacks and fixtures as well as repository tooling. Scripts consisting solely of top-level statements have no function row.
- [Capture, buffering and settings review](capture-and-buffering.md) examines the capture and publication workers, memory accounting, codec handling and settings reads.
- [Saved, metadata and playback review](saved-metadata-and-playback.md) examines catalog queries, sorting, polling, format inspection and candidates for removal.
- [Settings, destinations and diagnostics review](settings-destinations-and-diagnostics.md) examines repeated work in the destination publisher, diagnostics, startup discovery and the menu.

Tree-sitter enumerated definitions in tracked C, C++, JavaScript, Python and Bash sources. Ctags provided a second check of named C/C++ functions, including alternate entry points compiled from conditional signatures. Compiler-defaulted/deleted members are labeled separately. The loop count is syntactic, excludes nested functions and does not count work inside called APIs. The call column is a sample of at most twelve distinct callees, not a call graph. Third-party implementations in `native/vendor/` and generated build output are outside this review. The dispositions are static triage. “Keep” means no specific change was established for that entry. There are no per-function timing measurements.

## File boundaries and tools

Split `audio_history.cpp` by owned state and queue boundaries. Start with publication and retry scheduling, then capture ingress, then matcher decisions. Preserve lock ownership and the ordering of match, save, retry and release. Run the existing capture replay and memory-budget cases after each extraction. Leave `Worker` as the owner of event ordering. The detailed reviews identify smaller boundaries for the menu, metadata bridge and stream-dump writer.

For validation tools, both `validate_flac.py::validate` and `validate_showcase.py::validate` read a whole encoded recording into memory. Stream the container and update the hash incrementally if large-podcast validation is limited by peak RAM. Compare metadata, sample counts, hashes and error detection against the current tools. In `analyze_decoder_ownership.py::analyze`, an output or ambiguous binding can scan the capture history. An owner index and a maintained unresolved count could replace those scans. Verify the same violation messages on out-of-order, repeated and partially missing records before changing the analyzer.

The repository already has targeted Windows fixtures and replay runners. Keep these separate from production build dependencies and preserve the historical commands in dated validation records. Use the new paths under `tests/runners/` for current runs.
